# 多住户改造设计

当前的数据模型假设全世界只有一户人家：22 张表里没有任何租户键，3 张表的主键写死为 `1`，成员 id 写死为 `member-me`。这份文档描述怎么把它改成能同时服务多户，以及为什么这样改。

**范围**：数据模型与查询作用域。不包含登录鉴权——但第一节说明鉴权将来接在哪里。

---

## 一、租户 id 从哪来

整个改造里，真正昂贵的是「每一条查询都带上租户」这件事，涉及 **165 条 SQL** 中的 121 条。而「怎么知道当前是哪一户」只是一个函数。

把两者分开，是这份设计的核心：

```
resolveHousehold(request) → householdId
```

**第一阶段的实现**：从请求头或 cookie 读取一个格式合法的 id，读不到就回落到默认住户。这保持了今天的行为——单机自用的人什么都不用配。

**将来接鉴权时**：只有这个函数改，一百多条查询一条都不用动。

### 为什么是回落，而不是给每个访问者发一个新 id

判断依据是两种失败哪个更糟：

| 选项       | 失败长什么样                                |
| ---------- | ------------------------------------------- |
| 回落到默认 | 公开部署时，匿名访客共享同一份数据          |
| 强制独立   | 用户清掉 cookie，**数据永久孤儿，找不回来** |

没有鉴权时，cookie 是数据的唯一把手。第二种是数据丢失，而且没有补救路径；第一种正是今天的行为，不引入新问题。

所以做成一个开关：宽松模式回落，严格模式直接返回 401。接入登录那天改配置，不改代码。**回落时记一条日志**，真的部署之后能看出有多少匿名流量落进了默认住户。

## 二、表分成三层

划分依据是一个问题：**这份数据换一户人家看，还是不是同一份？**

### A 层 · 全局（不带租户键）

| 表                    | 说明                                             |
| --------------------- | ------------------------------------------------ |
| `flyer_sources`       | 新增。可自动同步的门店主数据，来自代码里的预设表 |
| `flyer_deals`         | 改为挂 `source_key`，不再挂某一户的门店行        |
| `flyer_deal_metadata` | 跟随 deal                                        |
| `flyer_price_history` | 改为按 `source_key` 累积                         |
| `flyer_sync_settings` | 同步本身变成全局任务，不再属于某一户             |

大统华本周的优惠，对所有人是同一份。**这是整个设计里最重要的一条。**

### B 层 · 租户（带 `household_id`）

| 域   | 表                                                                                                                      |
| ---- | ----------------------------------------------------------------------------------------------------------------------- |
| 基础 | `household_settings`、`household_members`、`recipe_preferences`                                                         |
| 库存 | `inventory_items`、`inventory_attachments`、`purchase_records`                                                          |
| 菜谱 | `recipe_catalog`、`recipe_attachments`、`recipe_cook_history`、`recipe_ratings`、`recipe_activity_log`、`meal_requests` |
| 采购 | `shopping_items`、`flyer_match_rules`、`flyer_recommendation_feedback`                                                  |
| 门店 | `household_stores`（新增，取代 `stores`）                                                                               |

### C 层 · 本阶段删除

`recipe_suggestions`、`recipe_favorites`。它们已经零写入方，只剩建表语句和一次性回填。

## 三、门店为什么要拆

现在的 `stores` 表混了两种东西，而它们的归属完全不同：

```
预设门店   有 source_key   可自动同步   目前 3 家，硬编码在代码里
手工门店   无 source_key   不能同步     id 是随机 UUID
```

拆开之后：

- `flyer_sources`（全局）持有可同步门店的身份、抓取地址、格式
- `household_stores`（租户）表达「这户人家关注哪些门店」，`source_key` 为空的就是手工门店

手工门店不参与同步，所以留在租户层是正确的。

### 但门店的全局身份目前并不存在

可同步的门店只有 3 家，写死在 `planner/route.ts` 的 `lougheedStores` 里，变量名就说明了它只覆盖一个片区。它们的 id（`store-hmart-coquitlam` 这类）是人手敲的，看着有规律，但**没有任何代码推导或强制这个规律**。而这 3 家里只有 PriceSmart 有结构化抓取，另外两家走模型搜网页的降级方案。

所以这一步不是「把已经存在的事实写进表结构」，而是**要从零建立一套门店身份体系**。至少三个问题这份设计还没有回答：

1. **谁往目录里加店。** 现在要改代码并重新部署。
2. **怎么判定是同一家店。** 两户人家各自手工添加了「大统华 Metrotown」，系统凭什么认定它们是同一家？名称、地址、还是连锁 id 加门店编号？判错了会把两家店的价格历史混在一起。
3. **长尾怎么办。** 只有一户人家关注的冷门小店，共享解析没有任何收益，却要占目录一条记录。

在这三点想清楚之前，`flyer_sources` 只能先按「代码预设 + 一次性导入」来建，把它当作一张真实的数据表，而不是当作已经解决的问题。

## 四、成本模型的变化

这是拆分带来的实际收益。

**现在**：优惠挂在某一户的门店行上。100 户都收藏了大统华，同一份 flyer 就要被解析 100 次，结果完全相同。定时任务每 6 小时遍历「收藏的门店」，模型调用量随用户数线性增长。

**改完**：按「来源 + 本周」解析一次，所有人共享。

```
模型成本   O(住户数 × 门店数)  →  O(门店数)
```

用户越多，单位成本越低。这一条决定了这个产品在商业上能不能成立，所以它必须和租户改造一起做——先做租户再回头拆 flyer，等于把 38 条 flyer 相关的 SQL 改两遍。

**这个收益有前提：只对进了目录的门店成立。** 目录现在有 3 家。手工添加的门店仍然是每户各算各的，因为没有别人和它共享。所以真实的成本曲线取决于目录能长多大，而那取决于上一节那三个问题怎么解决，属于产品问题而不是架构问题。

架构改造能做到的是：**让共享成为可能，并且不需要第二次改动数据模型**。

## 五、迁移

现有数据就是一户人家，全部归到一个固定 id。

**加列**：`ALTER TABLE ... ADD COLUMN household_id TEXT NOT NULL DEFAULT 'household-default'`。带默认值的加列会把已有行一次填好，不需要单独的回填语句。

**拆门店**：`stores` 里有 `source_key` 的行 → 建 `flyer_sources` 记录 + `household_stores` 订阅；没有 `source_key` 的行 → 只建 `household_stores`。

**优惠改挂来源**：`flyer_deals.store_id` 通过 `stores` 换成 `source_key`。

**成员 id 不迁移**。`member-me` 和 `member-family` 这两个固定 id 只需要不再出现在种子语句里——新住户改用随机 id。已有的行保留原 id，因为它们本来就是唯一的字符串，而 `meal_requests`、`recipe_ratings`、`recipe_cook_history` 都在引用它们。**动它们要连带改三张表，不动则零风险。**

## 六、分库纪律

单库多租户能用到 10GB。按现在实测的每户约 272KB、活跃住户估计每年约 5MB 计算，够 2000 户·年——足以验证产品是否成立。

但**必须从第一天就守住能拆分的前提**，否则将来迁移就是重写而不是搬运：

1. 每张 B 层表都有 `household_id`
2. 每一条读写 B 层表的语句都带 `household_id`
3. 不存在跨住户的查询

第 3 条是能分库的唯一前提，也是最容易在某次「临时查一下」时被破坏的。

**靠测试守住，不靠记性。** 做法与已有的 `schema-single-source.test.mjs` 一致：扫描 `app/api` 下所有 SQL 字面量，凡是提到 B 层表却不含 `household_id` 的即计入。建表模块是显式豁免项。

改造要分批进行，所以这条测试不能是「必须全部合规」——那样 CI 会一直红着，红久了就没人看了。改成**棘轮**：记录当前未作用域的语句数，只许降不许升；降了却没更新数字，同样判失败。基线是实测的 **111 条**。

降到 0 之后换成严格断言，闸门永久关上。

## 七、实施顺序

拆成七步，每一步都能独立通过测试并发布。中途停下也不会留下坏掉的状态：只有一户人家时，改过和没改过的表都落到同一个默认住户，功能不受影响。

| 步骤 | 内容                                                                             | 约涉及语句 |
| ---- | -------------------------------------------------------------------------------- | ---------- |
| 1    | `resolveHousehold` 解析器 + 棘轮测试                                             | —          |
| 2    | 基础域：settings、members、preferences                                           | 11         |
| 3    | flyer 分层：拆门店、优惠改挂来源、同步转全局                                     | 38         |
| 4    | 库存域：items、attachments、purchase_records                                     | 35         |
| 5    | 菜谱域：catalog、attachments、cook_history、ratings、activity_log、meal_requests | 37         |
| 6    | 采购域：shopping_items、match_rules、feedback                                    | 16         |
| 7    | 删除两张遗留表，移除回填                                                         | 6          |

### 为什么分批，以及为什么 flyer 排在第 3 位

**分批的理由是验证粒度，不是审查大小。** 加 `WHERE household_id = ?` 是机械动作，棘轮测试会抓漏。真正会出事的是三类问题：INSERT 漏列（`NOT NULL` 在运行时才炸，类型检查看不见）、JOIN 里加到了错误的别名上、以及动态拼接的 `IN (${placeholders})` 语句。这三类只有真跑才能发现，所以批次大小应当由「一次运行验证能覆盖多少」决定。

**flyer 分层提前**，是因为算「推迟的代价」时发现：flyer 表是全局层，第 4~6 步本来就不碰它们，推迟几乎免费——唯一的代价是 `stores` 那 9 条语句要改两遍（先加住户键，后来又拆成 `household_stores`）。既然如此，不如把它放在前面，让 `household_stores` 一次建成就带住户键。顺带 `flyer_recommendation_feedback.store_id` 要重新指向新结构，它属于采购域，flyer 先做则采购域一次改到位。

## 八、几个需要留意的点

**定时同步的时区。** 同步变成全局之后就没有「某一户的时区」了。优惠的有效期是门店当地的日期，所以应当跟随 `flyer_sources` 记录的门店时区，而不是任何一户人家的设置。这需要给 `flyer_sources` 加一个时区字段。

**演示数据的播种。** 现在的判断是「库存为空就播种」，改造后要变成「这户人家的库存为空」，否则第二户人家永远拿不到演示数据。

**附件的对象键。** R2 的 key 目前是 `inventory/{itemId}/{attachmentId}`。itemId 已经是 UUID，全局唯一，不需要加住户前缀。但删除时的清理必须同样带上住户作用域，避免删到别人的文件。

---

## 九、明确不做的事

**不做鉴权。** 第一节的解析器就是将来的接入点，届时不需要改任何查询。

**不迁 Durable Object。** 每住户一个 DO 在架构上更好，但那是把刚统一的数据层重写一遍。10GB 足够验证产品，且纪律守住之后迁移是机械工作。

**不引入 ORM。** 手写 SQL 在这个规模下没有问题，而且纪律测试正是靠扫描 SQL 字面量实现的。

**不解决门店身份体系。** 第三节列出的三个问题（谁加店、怎么判定同一家店、长尾怎么办）本阶段不回答。`flyer_sources` 先由代码预设一次性导入，结构上留出增长空间。**在这三个问题有答案之前，共享解析的收益只覆盖目录里那几家店。**这是这份设计里最大的未完成部分，写在这里以免被当成已经解决。
